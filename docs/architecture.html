The architecture

One process reads each counter and writes the record; every other program is handed the same seconds over a socket and draws from them. This is how that is built, function by function, and a review of where it is sound and where it is not.

A description of the program's structure and techniques with links to the code, followed by a software architecture review. Written against the working tree of 16 November 2026, commit cf8eb39.

Part one: how it is built

1. The processes, and who owns what

One process holds a counter's serial port. It is the only reader the port has, the only writer the log directory has, and it serves what it reads on a unix socket in that directory. Everything else attaches to the socket.

The port is exclusive because two processes reading one tty each get a share of the bytes and neither is told. Serial::open takes an advisory lock before it touches the line settings, and every radbeeper takes it:

src/serial.rs, lines 60 to 65

        // Advisory, and every radbeeper takes it -- which are exactly the
        // programs that would otherwise collide here.
        if unsafe { libc::flock(fd, libc::LOCK_EX | libc::LOCK_NB) } != 0 {
            unsafe { libc::close(fd) };
            return Err(OpenError::Busy);
        }

The lock argues for one reader. It does not argue for one consumer, and The stream is the report on the difference. The process that holds the lock starts a Server on the socket socket_path names, which is sock in the log directory, and publishes every second it reads.

2. The path of a count

A count is two bytes on a wire, then a number on a channel, then a line on a socket. Between the channel and the socket the process that owns the port does everything that is done once: averages for the log, the entropy pool, the spectrum row, the log row.

The wire. In heartbeat mode the counter sends a 16-bit count every second with no framing. The reader stays in step only by asking for exactly two bytes and giving up at a deadline. Serial::read_exact_or_timeout is the one primitive: count bytes, or fewer if the time runs out. Counter::next_raw is the stream on top of it:

src/counter.rs, lines 361 to 364

    pub fn next_raw(&self, timeout: Duration) -> Option<u16> {
        let r = self.port.read_exact_or_timeout(2, timeout);
        (r.len() == 2).then(|| u16::from_be_bytes([r[0], r[1]]))
    }

The top two bits are status flags; COUNT_MASK takes them off.

The reader thread and the channel. Bank holds one slot per counter ever seen, and one mpsc channel that every reader sends on. Bank::spawn starts a thread per counter that reads a second, stamps it with the wall clock and sends it. What it sends is a Tube:

src/main.rs, lines 1625 to 1632

enum Tube {
    Sample { who: usize, when: f64, counts: u32 },
    /// This tube stopped answering. Its slot stays reserved for its serial.
    Gone { who: usize },
    /// This tube's own thermometer, in degrees Celsius. Only from a bank
    /// that was told to ask, and a counter that has one. See `Bank::spawn`.
    Temp { who: usize, when: f64, celsius: f64 },
}

who is the counter's index in the bank, and a counter that is unplugged and put back keeps the index its serial had (Bank::adopt). Reading does not begin when the bank is made. Bank::start is separate from Bank::open because the flash download at start is a conversation on the same port, and a reader running during it takes the flash for counts.

The service loop. service is one loop on the main thread. Each turn lets in new clients (Server::accept_pending), looks every thirty seconds for a counter that was not there before (Prober, on threads of its own so a dead port holds nobody up), and takes one Tube from the bank. A sample goes to that counter's windows, to the room's windows, and out on the socket, in that order:

The socket. The protocol is lines of tab-separated text. Server::publish_sample keeps the sample in a ring and writes s, the index, the time and the count to every client. Live writes are non-blocking, and a client that does not take a line is dropped rather than waited for:

src/broker.rs, lines 397 to 407

    fn publish(&mut self, line: &str) {
        let bytes = line.as_bytes();
        self.clients.retain_mut(|c| match c.write_all(bytes) {
            Ok(()) => true,
            // A window that was closed, and a window that has stopped
            // reading, are the same thing from here and get the same
            // treatment. Neither is an error worth printing: people close
            // windows.
            Err(_) => false,
        });
    }

A client that attaches is given the greeting (hello, the protocol number, the server's spans, and a c line for each counter), then the ring, then the newest log rows, then the newest temperature of each counter, then live. That replay is why a window opened on a service that has been up all day has its eight-hour average at once:

src/broker.rs, lines 288 to 302

The ring is RING, 30,000 samples, and the rows are ROWS, 64.

The clients. Client::connect reads the greeting into an Identity. Client::poll gives one Event at a time and keeps three answers apart: an event, nothing yet, and the socket closed. The parsing is parse, and a line whose first word it does not know is skipped.

The terminal monitor turns an Event into a Tick (Tick::of) and, in watch, feeds the same types the service feeds: Windows, Ladder, Trail. The window does the same on a thread (feed), packs what the interface needs into a Snapshot about once a second, and sends it as the Update arm of Message. App::update stores it, App::view lays the widgets out and builds a Chart, and the canvas calls its draw.

Neither client computes a random line of its own. The hex on a client's screen is the one the server published, so there is one line and it is the one in the file.

3. The path of a temperature

The reader thread asks the counter its temperature in the gap after a second of counts, without stopping the stream. An answer is told from a count by its top bit, not by when it arrives. A temperature goes to a file of its own and to a line of its own on the socket, and nowhere a count goes.

The thermometer is the report, with the incident that fixed the design: the first version decided by timing, a slower firmware's answers arrived as the wait ran out, and three rows of one counter's log say about 6,600 counts in half a minute.

Only a service asks. service sets bank.temp_every; a monitor that holds the port itself leaves it None (the field's own comment in Bank says so). In Bank::spawn a counter is asked only if temp_supported names its firmware (a GMC-320 at Re 3.01 or later), only after two seconds of stream, and only while every second so far has carried STREAM_FLAG.

Counter::temp_in_stream writes <GETTEMP>> without flushing the input, then reads pairs until its wait (TEMP_WAIT_MS, 700 ms) runs out. This is the whole of the discrimination:

src/counter.rs, lines 416 to 421

            let raw = u16::from_be_bytes([head[0], head[1]]);
            if raw & STREAM_FLAG != 0 {
                samples.push(raw & COUNT_MASK);
                continue;
            }
            return StreamTemp { answer: self.late_answer(raw), samples };

A pair with the bit is a second of counts and is handed back in the samples of a StreamTemp, which the reader forwards as ordinary Tube::Samples. The first pair without it is the head of the answer. If the wait runs out first, the reader remembers that an answer is owed, and the next pair without the bit that turns up where a second was expected is taken as that answer by Counter::late_answer. The four bytes are decoded by decode_temp, which also knows the one answer that is not a temperature:

src/counter.rs, lines 153 to 164

pub fn decode_temp(r: &[u8]) -> TempAnswer {
    if r.len() != 4 || r[3] != 0xAA || r[1] > 9 {
        return TempAnswer::Garbled;
    }
    if r[0] == 85 && r[1] == 0 && r[2] == 0 {
        return TempAnswer::NotYet;
    }
    // Tenths as a whole number and ONE division, so 1A 01 is the double
    // nearest 26.1 and not a sum that lands one bit beside it.
    let v = (r[0] as f64 * 10.0 + r[1] as f64) / 10.0;
    TempAnswer::Degrees(if r[2] != 0 { -v } else { v })
}

The four results are the TempAnswer. NotYet is asked again in two seconds, five times at most, and after that at the ordinary spacing. Silent or Garbled three times running (TEMP_MISSES) and the counter is not asked again until it is next plugged in.

4. The record on disk

Everything is a tab-separated text file in one directory, named by what it is, whose it is and its month. A file is appended to by the process that holds the port and by nobody else. There is no rotation code, because a row is written to the file for its own month.

The directory is --logs, or what state_dir finds writable: /var/lib/radbeeper, then /var/log/radbeeper, then the user's own.

Backfill. The counter records to its own flash whether or not anything is listening. At each start, before the readers run, backfill_at_start measures the counter's clock against this machine's (Counter::clock_ahead), reads the newest end of the flash (read_history_tail, which uses find_history_end to bisect for the write pointer in a ring that has wrapped), and hands the bytes to backfill. That decodes them (samples), drops anything from the future or from the slot being logged now, cuts them into rows of the live logger's shape, and folds them in with merge. merge adds a row only to a slot that has none, so a live row is never replaced by one from the flash, and it writes a new file and renames it over the old one so an interrupted backfill leaves the old log whole. Then the counter's clock is set if it was out by more than a second.

The count log's characters are fixed: The log describes the format and section 8 how it is held to the Python program's.

5. The spectra

Radioactive decay arrives by chance, and the spectrum of chance is flat. Every spectrum here is the same sum with different windows, held against what chance would put in a bin, so that 1.0 means nothing is arriving on a schedule. There are four of them, for four lengths of time.

Spectrum is Welch's method: the mean removed, a Hann taper, a radix-2 transform, half-overlapped windows averaged. Spectrum::chance_max is how tall the tallest bin gets by luck for the number of averages behind it, and it is the line everything else is coloured against. Waterfall is the first version of the drum, a whole transform a row; it is still in the file and its comment is where the levelling is explained, but nothing outside its own tests constructs one now.

Trail is what both front ends and the spectrum log use. A row is joined from several windows that end at the same second: every bin of the shortest, and from each longer window only the bins longer than the one before could hold. Those few bins are worked out by direct sums and not by a transform, and a row is worked out only when it is asked for (Trail::rows), so a window handed eight hours of replay works out the rows on show and not three thousand on the way.

src/drum.rs is the shared paper. It holds no state. It says where a period stands across the paper, how hot a power is and how wide the pen is, in plain numbers, so the terminal and the window are two ways of putting ink where it says. The axis is cut into stretches at the windows' lengths (stretches) because the long periods have few bins and would otherwise take most of the width:

src/drum.rs, lines 98 to 103

pub fn place(axis: &[Stretch], period: f64) -> Option<f32> {
    let s = axis.iter().find(|s| period <= s.long && period >= s.short)?;
    let span = (s.long / s.short).ln();
    let t = if span > 0.0 { ((s.long / period).ln() / span) as f32 } else { 0.0 };
    Some(s.left + t.clamp(0.0, 1.0) * (s.right - s.left))
}

shade_of turns a power into one of 64 shades by its logarithm against the luck line, heat gives a shade its colour as three numbers and no colour type of anybody's, pen its width, front_row joins the hours-long averages into the row at the front, and strength says how strongly a whole row is inked.

src/longdrum.rs makes the long papers from the count log, so they exist for every day there is a log for, including the days before the code was written. The drum spectrogram and The monthly record are the reports. The steps:

The terminal monitor is one function, watch, of 1,043 lines. It owns the screen through Screen (raw mode, restored on drop), wakes ten times a second for the keys, and redraws the whole screen into one string on every sample. 9. Techniques worth naming

Exact-length reads with a deadline, on a protocol with no framing. Every reply from the counter is a fixed number of raw bytes. The only way to stay in step is to ask for exactly that many and stop at a deadline. A conversation flushes the input first; the stream never does.

src/counter.rs, lines 167 to 172

    fn ask(&self, cmd: &[u8], want: usize) -> Vec<u8> {
        self.port.flush_input();
        let _ = self.port.write_all(cmd);
        self.port
            .read_exact_or_timeout(want, Duration::from_millis(1000))
    }

Where a reply runs past what was asked for (both GMC-320s answer a 2,048-byte flash read with 2,049), a flush is not enough, because the spare byte is still in flight. Serial::drain reads until the line has been quiet for 20 ms. The comment in Counter::read_history is the account of the corrupt flash that turned out to be this.

The flag-bit discriminator. What a pair of bytes is, is decided by what it is. The excerpt is in section 3. The stream's own top bit separates a second of counts from the head of an answer, and a stream that does not carry the bit is never asked.

Replay on attach. A client starts complete: the greeting, the ring, the rows, the temperatures, then live. The excerpt is in section 2. The replay is written blocking with a five-second deadline and live traffic is non-blocking, so a client that is reading gets all of it and one that is not costs the counter nothing.

One row per slot. A row's identity is floor(time / interval). The live writer, the restart and the backfill's merge all refuse a second row for a slot, which is what lets a flash download be folded into a log that was being written live. The excerpt is in section 4.

Dealing a log row across bins. A row is thirty of the counter's seconds, which is a little over thirty of ours, so rows dropped whole into thirty-second bins by their middles leave an empty bin every quarter of an hour. Counts::binned gives each bin the share of the row that lies in it:

src/longdrum.rs, lines 196 to 212

        for &(mid, counts, seconds) in &self.rows[from..] {
            let (a, b) = (mid - seconds / 2.0, mid + seconds / 2.0);
            if a >= end {
                break;
            }
            if b <= start {
                continue;
            }
            let first = (((a - start) / bin).floor().max(0.0)) as usize;
            let last = ((((b - start) / bin).ceil()) as usize).min(n);
            for (k, cell) in sums.iter_mut().enumerate().take(last).skip(first) {
                let (lo, hi) = (start + k as f64 * bin, start + (k + 1) as f64 * bin);
                let share = (b.min(hi) - a.max(lo)).max(0.0);
                cell.0 += counts * share / seconds;
                cell.1 += share;
            }
        }

A bin is counted only when at least half of it was covered.

Folding bands by the mean. A day has 720 periods between two minutes and itself and the paper has 192 places. The loudest of the periods that share a place is high by construction, and a row of those is a wall. Each band is the mean power of its periods, at the geometric mean of their periods, and a band no period fell in is left out:

src/longdrum.rs, lines 289 to 293

        .collect();

Part two: a software architecture review

The process design is right and the record's rules are right. The weaknesses are in how the code is divided: three copies of the loop that consumes the stream, two front ends that have begun to disagree, a reference implementation whose reason for existing has changed, and several failures that are swallowed.

Each finding below gives the evidence in the code, a recommendation and a rough size: small is an afternoon, medium is a few days, large is a week or more.

What is sound

One reader, many consumers. The lock is taken before the line settings are touched, the server never reads from a client, and the window cannot open a port because its crate has no code for one. Live writes to clients are non-blocking, so no client can stop the logger.

The record's invariants. One row per slot, a file per counter per month, a merge that never replaces a live row and renames a whole file into place, columns matched by name and not by position. These are few, they are stated where they are enforced, and the tests exercise them.

Counts and everything else are kept apart. A temperature goes to its own file and its own line. The merged room is a second file beside the per-counter files, with the per-tube counts in it so it can be taken apart again. The pinned count log was not touched to add either.

The arithmetic is in the library and has no opinion about drawing. src/drum.rs returns fractions and three floats, src/analysis.rs returns numbers, and both front ends and the page use them.

The comments record why. Nearly every non-obvious line has the incident that put it there, with a date. A reviewer can check a claim against the code, which is how most of what follows was found.

The findings

1. The stream is consumed in three hand-written loops

This is a real problem, and it is the root of several others.

The service, the terminal monitor and the window each contain the code that turns samples into a room's state. The whole-second sum for the spectrum, sec_bin and sec_sum, is written out three times: in service, in watch and in feed. So is the handling of a counter joining, a counter going quiet, and the rule that the replay is not poured into the entropy pool. mean_cpm and mean_of are the same three lines. STRIP_KEEP is defined in both files with the same value.

The copies have already drifted. The join tolerances of the two prefills in section 6 are 600 seconds and 120: after a service has been stopped for five minutes, the terminal fills its averages from the log and the window does not. The long papers' luck line, which decides where the pen turns from green to hot, is 5.0 in the window (LONG_LUCK) and on the page (LUCK), and in the terminal it is long_luck, which is chance_max_of(192, 1.0) and comes to about 7.7 (1 + √(2 × ln 191) + 2 × ln 191 / 3). The same band at six times chance is hot in the window and green in the terminal.

Recommendation. Put one type in the library, fed broker::Events, that owns the windows for each counter and the room, the whole-second sum, the ladder, the trail, the arrival strip and the prefill, and gives each front end a read-only view. The service can use the same type for the parts it shares. Each front end then keeps only layout and ink. Medium. The existing unit tests of both prefills become tests of one.

4. The long drums pool counters of different sensitivity

A real problem when two counters are not alike, and the bench's are not.

Counts::load reads every counter's rows into one list, and Counts::binned divides the summed counts by the summed seconds. The comment calls the result "the room's rate for one tube however many were listening". That holds only if every tube counts the room at the same rate. If one reads 20 counts a minute and the other 40, the pooled figure is 30 while both listen and 20 or 40 when one is away, so a counter joining or leaving is a step in the series the transform is given. The scatter that powers are held against is taken from neighbouring differences and hardly sees a single step, so the step's power is not normalised away; it lands in the long-period bands.

The effect on a line's content is already recorded: the commit of 16 November that relaxed the sample month's test (ed91831) notes that through the week a second tube counts beside the first, the first tube's twenty-minute rhythm is half as deep in the pooled rate and its power a quarter.

The live spectrum has the same shape of problem. The service, the monitor and the window all feed the whole second summed across counters to the ladder and the trail, so one of two counters going quiet halves the series. The averages were moved to tube-seconds for exactly this reason (Windows::mean); the spectrum's input was not.

Recommendation. Make a line per counter and pool the spectra, or divide each counter's rate by its own long mean before pooling so that every tube reads 1.0 on an ordinary day. For the live drum, feed the mean of the counters answering, not the sum. Medium, and the kept lines in drum-day.tsv would need writing again, which keep can do because the count log is the record.

Real, and cheap to fix. What happens when the log directory cannot be written depends on which file, and none of it is loud.

The count log is the one failure that stops the service, and it stops it by leaving the loop:

8. The socket protocol has a version and no capabilities

A real gap, small today. The rule in PROTOCOL, that a line may be added without a bump and an unknown line is skipped, is sound and has worked: the t line was added that way. Three things it does not cover.

A client cannot tell what a server will never send. A monitor attached to a service started with --no-temp, or to another monitor that holds the port, sees no t line and cannot say whether the temperature is not asked or has not come yet. The greeting carries the spans and not the log interval, so the window assumes it: every: log::DEFAULT_LOG_EVERY is what places the log-row ticks on the counts, whatever --log-every the service was given.

A version mismatch is indistinguishable from nobody serving. Client::connect returns None for a greeting whose number is not exactly its own:

The replay ring is shared. RING is 30,000 samples in all, and its comment says a client's 30,000-second window is full if the service has been up that long. With two counters the ring holds 15,000 seconds of each.

That argues against relying on it for a continuous record; it does not argue against recording while it is open, which is what it does for the counts.

Recommendation. Let a monitor that owns the port and is logging ask at the same interval and write the same file. The reader thread already does the asking; watch needs the setting and the write. Small.

11. The stream has no way back into step

This is an inference from the code; it has not been seen to happen. Counter::next_raw reads two bytes and takes them for a second. If a single byte is ever lost on the line, every pair after it is the low byte of one second and the high byte of the next, and nothing in the reader looks for that. Before 16 November there was nothing to look with. Now there is: on a stream that has always carried STREAM_FLAG, a pair without it when no temperature answer is owed is, by the reader's own reasoning, not a second of counts. Today that case sets marked = false, stops asking the temperature, and sends the pair on as a count. A misaligned pair made of a low byte of 1 and a high byte of 0x80 would be logged as 384 counts in a second.

Recommendation. In that case, do not count the pair; drop one byte, and require the flag on the next few pairs before counting again. Add a fake-counter test that swallows one byte. Small. Whether a real adapter ever drops a byte is not known, and the cost of handling it is low.

12. The thread model is simple, and one invariant rests on a comment

Mostly sound. In the service: the main thread owns the server, the windows, the pools and the loggers; one reader thread per counter and the prober's threads send on channels; a flash download for a counter plugged in later runs on its own thread and hands the counter back on a channel; keep runs on a thread that only reads the count log and appends to its own files. The only shared state is each Arc<Counter>, an AtomicBool for the stop signal and a OnceLock for one setting. In the window, the feed thread owns the state and the interface gets immutable snapshots and Arcs.

Two things to know. The rule that no conversation happens on a port while its reader runs is what Bank::start exists for, and its comment records that breaking it put 16,383 counts a second into the log twice. It is kept by the order of calls. Bank::live hands out the Arc<Counter> to any caller at any time, and every method of Counter takes &self. And the release profile sets panic = "abort", so a panic on any thread, including the keep thread or a prober, ends the service. The comments in service record one panic that did, an index out of bounds seven minutes after a second counter joined. Whether the init script restarts it is in the Copal repository and was not checked.

Recommendation. Make the reader own its Counter while it runs, and give the bank a handle that can only stop it; a conversation then needs the counter back, and the type system keeps the rule. Medium, and it fits the move in finding 2.

13. What the tests do not reach

The window's drawing and its clicks are untested. The window's 34 tests cover the arithmetic under the drawing: where regions fall, what a pen's shade is, the PNG writer, the needle's ballistics, seconds_from_log. None constructs a Chart. The test named for clicks exercises next_open, the rule for which drum opens next; Chart::pressed, which maps a point to a message, and Chart::draw are not called by any test. The pictures were checked by eye, with --shot.

A timezone dependence was found on 16 November, by CI and not by a local run. The sample month's test asked every whole day for six times chance at twenty minutes. Cut at Pacific midnight every day cleared six; cut at UTC's one day read 4.95. Every machine the tests had been run on was on the bench's clock. The fix was to ask for three, and the commit records the suite passing under six zones.

The cause is structural and worth stating once. stamp writes local wall-clock time with no offset, and parse_stamp reads it back in the reader's zone. A day is cut at local midnight (day_start). So the same log gives different day lines on machines in different zones, the published pages are built by a workflow that sets no timezone, on a runner that need not be in the zone the log was written in, and the hour that repeats when the clocks go back is ambiguous in the per-counter log. The merged log carries a unix column for this reason; the per-counter log cannot, because its characters are pinned.

Recommendation. Run the Rust tests in CI under two zones, one of them not UTC. For the window, a test that builds a Chart from a fixed Snapshot, calls pressed at the centre of each tile and thermometer, and checks the message, needs no renderer. A golden picture through the software renderer and png_of is possible but is medium; the click test is small. The offset in the per-counter log belongs with finding 7.

14. The 85.0 sentinel and the flag bit rest on two units

Not a problem as built; a known limit. decode_temp refuses exactly 55 00 00 and nothing near it, and a counter is asked again a few times and then at the ordinary spacing, so a firmware that rests at some other value would log that value. The flag-bit assumption is guarded at run time and fails safe: a stream without the bit is not asked. What is not guarded is a firmware that sets the bit on its seconds but answers in more than four bytes, or whose answer is preceded by something else. The fake counter encodes what the two units on the bench do, so the tests prove the reader against the belief and not against other hardware. The thermometer says this in its own section 8.

Recommendation. Nothing to build. When a third firmware is on the bench, run the forty-second mid-stream test from that report against it before trusting its temperature file, and record the result there.
